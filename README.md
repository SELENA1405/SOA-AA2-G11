# S18 Club Equipment Transport Planner

Additional Assessment 02 (AA-02), course 128-353 Application Development on Service-Oriented Architecture, Group 11.

## Project Overview

Scenario S18 is a Club Equipment Transport Planner. A club member opens a load plan for their session, adds equipment types with a unit count from 1 to 15, edits or removes lines, and sees the total mass in kilograms. The total is calculated by the server (the sum of unit count times unit mass), so the web page only displays what the server returns.

The system has three layers that run as three containers started with Docker Compose: a static web page served by Nginx, a FastAPI backend, and a PostgreSQL database. The project shows the three parts working together, the container setup, and the testing and debugging evidence. The evidence is in the `evidence/` folder: `integration-evidence.md`, `testing-debugging-evidence.md` and `contribution-evidence.md`.

## Setup Instructions

1. Install Docker with Docker Compose v2 and check `docker version` and `docker compose version`.
2. Open a terminal at the project root (the folder that contains `submission-manifest.yml`).
3. Optional: copy `config/.env.example` to `config/.env` and change the values. Without it, Compose uses the same development defaults.
4. Run `docker compose -f config/docker-compose.yml config` to see the resolved configuration.
5. Make sure ports 8080 and 8000 are free, then start the stack with the command under Run Instructions.

Environment handling: the database name, user and password are read from environment variables (`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`), with development defaults in `config/docker-compose.yml`. `config/.env.example` documents them. A real `config/.env` is ignored by Git (`config/.gitignore`) and must not be submitted. The backend's `DATABASE_URL` is built in the Compose file from the same three values, so the credentials are written in one place only. The defaults are for local development and must not be used for a public deployment.

The SQL files in `database/` run only when the database volume is created for the first time. After changing them, reload with `docker compose -f config/docker-compose.yml down -v` and start again. This deletes the stored data.

Configuration verification: setup was tested on Sat 21 Nov 2026 on macOS with Docker Desktop. `docker compose -f config/docker-compose.yml up --build -d --wait` created the network and a new volume and started all three services, and the database, backend and frontend all reached the healthy state. `GET http://127.0.0.1:8080/api/health` (through Nginx) and `GET http://127.0.0.1:8000/api/health` (direct) both returned `{"status":"ok","database":"connected"}`. The run was made without a `config/.env` file, so the defaults were used. After that, the four required S18 cases passed through the browser, Postman and `psql`; the logs and screenshots are in `evidence/`.

## Run Instructions

```sh
docker compose -f config/docker-compose.yml up --build -d --wait
docker compose -f config/docker-compose.yml ps
docker compose -f config/docker-compose.yml logs backend database
docker compose -f config/docker-compose.yml down
```

- Open http://127.0.0.1:8080 for the web page. Select equipment, enter a quantity from 1 to 15 and click "Add to Plan". Use "Update" and "Remove" in the plan table to change or delete a line.
- API documentation (generated by FastAPI): http://127.0.0.1:8000/api/docs.
- `down` keeps the database volume. Add `-v` to remove it as well.
- Backend unit tests: install pytest (`python -m pip install pytest`), then run `python -m pytest` inside the `backend` folder.
- Postman: import `evidence/assets/S18-postman-collection.json`, set `baseUrl` to `http://127.0.0.1:8080/api` and run the collection.
- On Windows PowerShell, use `curl.exe` instead of `curl`.

## API Endpoints

All routes are under `/api`. Errors use the body `{"error_code": "...", "message": "..."}`.

| Method and path | Success | Errors |
|---|---|---|
| GET /api/equipment-types | 200, list of equipment | none |
| GET /api/equipment-types/{equipmentCode} | 200 | 404 EQUIPMENT_NOT_FOUND |
| POST /api/load-plans (header `X-Session-Code`) | 201 new plan, 200 existing plan | 400 INVALID_REQUEST |
| GET /api/load-plans/{planCode} | 200, items and `totalMassKg` | 404 PLAN_NOT_FOUND |
| POST /api/load-plans/{planCode}/items | 201 | 400 INVALID_UNIT_COUNT, 400 INVALID_REQUEST, 404 EQUIPMENT_NOT_FOUND, 404 PLAN_NOT_FOUND, 409 DUPLICATE_ITEM |
| PUT /api/load-plans/{planCode}/items/{equipmentCode} | 200 | 400 INVALID_UNIT_COUNT, 404 EQUIPMENT_NOT_FOUND, 404 PLAN_NOT_FOUND |
| DELETE /api/load-plans/{planCode}/items/{equipmentCode} | 204 | 404 EQUIPMENT_NOT_FOUND, 404 PLAN_NOT_FOUND |

A plan belongs to the session in the `X-Session-Code` header; another session gets 404 PLAN_NOT_FOUND. `unitCount` must be a whole number from 1 to 15. Request bodies: `{"equipmentCode": "EQUIP-001", "unitCount": 2}` to add a line and `{"unitCount": 3}` to update it.

## Known Limitations

- The session code is a random identifier created by the page and is not authentication. It lives for one page load, so reloading the page starts a new plan.
- The catalogue has two equipment types (EQUIP-001 and EQUIP-002) and the page has no screen to add more.
- Plans are never deleted or expired.
- The quantity boxes in the plan table accept typed values outside 1 to 15. The server rejects them with `INVALID_UNIT_COUNT` and the page shows the error, so this is handled but not prevented in the browser.
- Automated tests cover the domain rules only. The API, browser and database behaviour was tested by hand with Postman, Chrome DevTools and `psql`.
- The setup was tested on macOS only, and the stack has no HTTPS. The development credentials are not suitable for a public deployment.

## Containerisation and Deployment Concepts

**Containers and virtual machines.** A virtual machine emulates hardware and runs a full guest operating system. A container shares the host's kernel and isolates only the process, its files and its network, so it starts in seconds and is much smaller. Here three containers (Nginx, FastAPI and PostgreSQL) run on one host, and the Dockerfile makes the backend image reproducible on any machine.

**Operating system.** Containers rely on Linux kernel features (namespaces for isolation and cgroups for resource limits). On macOS and Windows, Docker Desktop runs a small Linux virtual machine to provide that kernel.

**Container networking.** Compose creates a private network in which services reach each other by service name. The backend connects to the host `database` on port 5432, and Nginx proxies `/api/` to `backend:8000`. Only ports 8080 and 8000 are published to the host. The browser calls the same origin (port 8080), so no CORS configuration is needed.

**Persistence.** A container's filesystem is discarded when the container is removed, so the PostgreSQL data lives in the named volume `scenario-data`. SQL files in `docker-entrypoint-initdb.d` run only when that volume is empty.

**Configuration and secrets.** Settings are supplied as environment variables, with documented defaults in the Compose file and `config/.env.example`. The real `config/.env` is git-ignored. This follows the idea of keeping configuration out of the code.

**Cloud and CI/CD readiness.** The same images could be deployed to a cloud container service. That would additionally need real secrets from a secret store, HTTPS, a managed or backed-up database, and health checks. A CI pipeline could run `docker compose config`, build the images, start the stack and run the unit tests and the Postman collection. Building such a pipeline is outside this assessment.
